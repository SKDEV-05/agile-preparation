Le module **M204 : Développer en front-end** s'inscrit au cœur du parcours des développeurs Web Full Stack. ## 2. MODULE 1 (PDF 1) : APPRÉHENDER LES FONDAMENTAUX DU WEB FRONT-END

### 2.1 Fondamentaux des sites web statiques
Un site web statique repose sur un ensemble de fichiers **HTML**, **CSS** et **JavaScript** préexistants hébergés sur un serveur web (Apache, Nginx, ou un hébergement d'objets statiques tel que GitHub Pages ou AWS S3).

#### Caractéristiques essentielles :
1. **Contenu préétabli** : Chaque visiteur télécharge exactement le même code HTML.
2. **Absence de logique dynamique serveur** : Pas d'interrogation dynamique de base de données à la volée côté serveur (aucun code PHP, Python, ou Node.js actif générant la page au moment de la requête).
3. **Mise à jour manuelle** : Pour modifier un texte ou une image, le développeur doit éditer le fichier source et le redéployer.
4. **Cas d'usage appropriés** : Sites vitrines simples, portfolios de développeurs, CVs en ligne, documentations statiques, pages de mentions légales.

#### Le cycle Requête / Réponse classique :
```
[Client / Navigateur] ──── (1) Requête HTTP GET /index.html ────> [Serveur Web Statique]
                      <─── (2) Renvoi du document HTML brut ─────
[Client / Navigateur] ──── (3) Requête HTTP GET /style.css ─────> [Serveur Web Statique]
                      <─── (4) Renvoi du fichier CSS ────────────
[Client / Navigateur] ──── (5) Requête HTTP GET /script.js ────> [Serveur Web Statique]
                      <─── (6) Renvoi du script JavaScript ──────
```
Le navigateur parse ensuite le HTML pour construire le **DOM (Document Object Model)**, parse le CSS pour construire le **CSSOM (CSS Object Model)**, combine les deux dans un **Render Tree** pour calculer la mise en page (*Layout*) et effectue le tracé des pixels à l'écran (*Paint*). Le JavaScript s'exécute localement pour apporter de petits comportements interactifs (ouverture de modals, validation de champs, carrousels légers).

### 2.2 Architecture Client-Serveur et séparation Front-End / Back-End

Le développement web moderne repose sur une séparation hermétique des responsabilités :

```
                  ┌────────────────────────────────────────────────────────┐
                  │                 FRONT-END (Côté Client)                │
                  │  Navigateur Web : Interface Utilisateur, UX, Réactivité │
                  │  Technologies : HTML5, CSS3, JavaScript ES6+, React    │
                  └───────────────────────────┬────────────────────────────┘
                                              │
                     Échanges de données JSON │ Requêtes HTTP (Fetch/Axios)
                                              │ REST API / GraphQL
                                              ▼
                  ┌────────────────────────────────────────────────────────┐
                  │                 BACK-END (Côté Serveur)                │
                  │  Serveur d'application : Logique Métier, Sécurité      │
                  │  Technologies : Node.js (Express), Python, PHP, Java   │
                  └───────────────────────────┬────────────────────────────┘
                                              │ Requêtes SQL / NoSQL
                                              ▼
                                   ┌─────────────────────┐
                                   │   BASE DE DONNÉES   │
                                   │ PostgreSQL, MongoDB │
                                   └─────────────────────┘
```

#### Tableau comparatif : Front-End vs Back-End

| Critère | Front-End (Client) | Back-End (Serveur) |
| :--- | :--- | :--- |
| **Lieu d'exécution** | Navigateur web du client (PC, mobile, tablette) | Serveurs physiques, machines virtuelles, conteneurs Docker |
| **Rôle principal** | Affichage de l'interface, capture des actions utilisateur, animations | Traitement métier, calculs lourds, authentification, persistance |
| **Technologies clés** | HTML5, CSS3, JavaScript/TypeScript, React, Vue, Angular | Node.js, Express, Spring Boot, Django, Laravel, ASP.NET |
| **Format des données** | Reçoit du JSON, manipule le DOM pour afficher du HTML stylisé | Lit la base de données, applique les règles métier, renvoie du JSON |
| **Sécurité** | Code public, visible et inspectable par l'utilisateur (DevTools) | Code privé, sécurisé, accès direct aux credentials et clés secrètes |

### 2.3 Émergence et rôle des Frameworks Front-End
Historiquement, la manipulation du DOM s'effectuait à l'aide de l'API JavaScript native (`document.getElementById`, `document.querySelector`) ou avec des bibliothèques d'assistance comme **jQuery**. 

Cependant, lorsque les interfaces sont devenues massives (ex: Facebook, Twitter, Trello), cette approche impérative a montré des limites critiques :
* **Code "Spaghetti"** : Mélange intriqué entre la logique métier, la persistance de l'état et la mise à jour manuelle des nœuds du DOM.
* **Perte de performance** : Les lectures et écritures répétées dans le DOM réel déclenchent des phases coûteuses de recalcul de style (*Reflow*) et de redessin (*Repaint*).
* **Manque de cohérence de l'état** : Si une donnée change à un endroit (ex: nombre d'articles dans un panier), le développeur devait penser à mettre à jour manuellement tous les éléments HTML concernés. En cas d'oubli, l'interface affichait des informations contradictoires.

**Apport des Frameworks et Bibliothèques modernes :**
* Fournir une **architecture composable et modulaire**.
* Automatiser la synchronisation entre l'état en mémoire et l'affichage à l'écran grâce à une **approche déclarative**.
* Optimiser les performances de mise à jour grâce à des technologies de rendu virtuel (**Virtual DOM**).

### 2.4 Concept clé : Single Page Application (SPA) vs Multi-Page Application (MPA)

#### 1. L'application multi-pages classique (MPA)
Dans une MPA traditionnelle (ex: sites PHP/WordPress, sites e-commerce anciens) :
* Chaque clic sur un lien `<a href="/contact.html">` envoie une requête HTTP complète au serveur.
* Le serveur génère ou lit la nouvelle page HTML et la renvoie en intégralité.
* Le navigateur **détruit complètement la page actuelle**, affiche un écran blanc pendant quelques millisecondes, puis reconstruit toute la nouvelle page (y compris l'en-tête, le pied de page et la barre latérale qui n'ont pourtant pas changé).

#### 2. L'application monopage moderne (SPA)
Dans une SPA (ex: Gmail, Netflix, Spotify, interfaces React) :
* Lors de la première visite, le navigateur charge un fichier HTML quasi-vide (qui contient juste `<div id="root"></div>`) et un gros fichier JavaScript contenant l'ensemble de l'application.
* Une fois ce chargement initial effectué, **le navigateur ne rechargera plus jamais la page**.
* Lorsque l'utilisateur clique sur un lien de navigation, le code JavaScript intercepte l'événement, met à jour l'URL visible dans la barre d'adresse grâce à l'API HTML5 `History`, et modifie instantanément les composants affichés à l'écran en injectant les nouveaux éléments dans le nœud racine.
* Si des données sont nécessaires, le JavaScript lance une requête discrète en arrière-plan (Fetch/Axios) vers une API REST, reçoit un simple payload JSON, et met à jour les zones de texte correspondantes.

#### Tableau comparatif : SPA vs MPA

| Critère d'évaluation | Single Page Application (SPA) | Multi-Page Application (MPA) |
| :--- | :--- | :--- |
| **Nombre de pages HTML réelles** | **Une seule** (`index.html`) | Multiples (`index.html`, `about.html`, etc.) |
| **Rechargement du navigateur** | **Aucun** (navigation instantanée et fluide) | **Systématique** à chaque changement de page |
| **Expérience utilisateur (UX)** | Fluide, dynamique, identique à une application native mobile | Saccadée par les flashs blancs de rechargement |
| **Temps de chargement initial** | Plus lent (téléchargement du bundle JS complet) | Plus rapide (seul le HTML/CSS de la page demandée est chargé) |
| **Temps de navigation ultérieure** | **Quasi-instantané** (seul le JSON de données circule) | Lent (rechargement de l'ensemble des assets) |
| **Référencement naturel (SEO)** | Plus délicat (nécessite SSR comme Next.js ou pré-rendu) | Naturellement excellent (chaque page est un HTML complet) |
| **Complexité de développement** | Plus élevée (gestion du routage client, de l'état, de la mémoire) | Plus faible sur les sites simples de contenu |

### 2.5 Fonctionnement interne, avantages et contraintes d'une SPA

```
                    FONCTIONNEMENT D'UNE REQUÊTE DANS UNE SPA :
                    
   Client (Navigateur)                                        Serveur
           │                                                     │
           ├──────── 1. Requête initiale GET / ─────────────────>│
           │<─────── 2. Réception de index.html + bundle.js ─────┤ (Chargement unique)
           │                                                     │
   [Affichage de l'UI]                                           │
           │                                                     │
   [Clic de l'utilisateur sur "Voir Profil"]                    │
           │                                                     │
           ├──────── 3. Requête Fetch GET /api/user/42 ─────────>│ (Uniquement de la donnée !)
           │<─────── 4. Réponse JSON : {"nom": "Sara", ...} ─────┤
           │                                                     │
   [Mise à jour ciblée du DOM par React sans recharger la page]  │
```

#### Synthèse des Avantages et Inconvénients d'une SPA :
* **Avantages majeurs** :
  1. **Réactivité exceptionnelle** : Réduction drastique de la bande passante consommée car on ne transporte plus d'éléments de structure répétés (headers, footers), mais uniquement du JSON brut de quelques kilo-octets.
  2. **Séparation claire des équipes** : L'équipe Front-End consomme des APIs sans se préoccuper du langage serveur ; l'équipe Back-End fournit des endpoints documentés sans écrire une seule ligne de CSS.
  3. **Portabilité** : La même API Back-End sert simultanément le site Web (React), l'application mobile (React Native) et d'éventuels clients tiers.
* **Contraintes à anticiper** :
  1. **Taille du bundle initial** : Si l'application n'est pas fractionnée en sous-modules (*Code Splitting*), le premier affichage peut être ralenti sur les connexions faibles.
  2. **Fuites de mémoire potentielles** : Comme la page ne se recharge jamais, les écouteurs d'événements et intervalles non nettoyés peuvent s'accumuler en RAM.

### 2.6 Exercices d'évaluation et synthèse du Module 1

#### Question 1 : Pourquoi une SPA demande-t-elle généralement une configuration de redirection spécifique sur le serveur d'hébergement ?
* **Réponse détaillée** : 
  Dans une SPA, les routes comme `/dashboard` ou `/produits/42` n'existent pas sous forme de dossiers ou de fichiers physiques sur le disque dur du serveur. Si un utilisateur recharge la page sur `https://monsite.com/dashboard`, le serveur HTTP (Apache ou Nginx) cherchera un fichier nommé `dashboard` ou `dashboard/index.html` et renverra une erreur **404 Not Found**. 
  Pour corriger cela, il faut configurer une règle de réécriture d'URL (*Fallback Rule*) qui redirige **toutes les requêtes entrantes** vers l'unique fichier racine `index.html`. C'est ensuite le routeur JavaScript client (React Router) qui lit l'URL demandée et affiche le bon composant.

#### Question 2 : Citer deux cas d'usage où une architecture MPA reste préférable à une SPA pure.
* **Réponse détaillée** :
  1. **Sites de contenu ou blogs axés sur le référencement (SEO)** : Les moteurs de recherche indexent plus rapidement et sans artifice les pages HTML statiques servies pré-remplies.
  2. **Sites e-commerce grand public simples** : Les utilisateurs y accèdent souvent ponctuellement via des liens publicitaires précis où le temps de chargement de la toute première page (LCP - Largest Contentful Paint) doit être inférieur à une seconde pour maximiser la conversion.

## 3. MODULE 2 (PDF 2) : PRÉPARER REACT — MAÎTRISER LE JAVASCRIPT MODERNE (ES6+)

> **Pourquoi tant de développeurs échouent sur React ?**
> React n'est pas un langage distinct : c'est du JavaScript moderne pur. 90% des difficultés rencontrées par les débutants avec React (hooks, immutabilité, props, re-rendus) sont en réalité des lacunes sur les concepts fondamentaux introduits par **ECMAScript 2015 (ES6)** et ses révisions successives.

---

### 3.1 Variables et portées : var, let et const

Avant 2015, `var` était le seul mot-clé pour déclarer des variables en JavaScript. `var` souffre de défauts structurels majeurs que `let` et `const` sont venus éliminer.

#### 1. Les pièges de `var` :
* **Portée de fonction (Function Scope)** : Une variable `var` déclarée à l'intérieur d'un bloc `if` ou d'une boucle `for` s'échappe de ce bloc et devient accessible dans toute la fonction englobante.
* **Le Phénomène de Hoisting (Remontée)** : Les déclarations de `var` sont automatiquement "remontées" au sommet du contexte d'exécution lors de la phase de compilation. La variable existe avant même la ligne de son écriture, avec la valeur `undefined`.
* **Redéclaration autorisée sans avertissement** : Réécrire `var x = 10; var x = 20;` ne produit aucune erreur, ce qui favorise les écrasements accidentels de variables dans les grands scripts.

```javascript
// Exemple illustrant le Hoisting et la fuite de portée avec var :
console.log(prenom); // Affiche "undefined" (au lieu de lever une erreur ReferenceError)
var prenom = "Sara";

if (true) {
    var age = 22; // Déclaré dans le bloc if
}
console.log(age); // Affiche 22 ! La variable s'est échappée du bloc if.
```

#### 2. La rigueur de `let` et `const` :
* **Portée de bloc (Block Scope)** : Toute variable déclarée avec `let` ou `const` n'existe **strictement qu'à l'intérieur des accolades `{}`** où elle est définie.
* **Temporal Dead Zone (TDZ)** : Bien que les déclarations `let` et `const` soient identifiées lors de la compilation, elles ne sont pas initialisées. Tenter de les lire avant leur ligne d'assignation lève une exception immédiate `ReferenceError`.
* **Interdiction de redéclaration** : Dans le même bloc, il est impossible de redéclarer une variable portant le même nom.

```javascript
// Exemple avec let et const :
// console.log(ville); // Erreur fatale : ReferenceError (dans la Temporal Dead Zone)
let ville = "Casablanca";

if (true) {
    let message = "Bonjour";
    const TVA = 0.20;
    // TVA = 0.25; // Erreur fatale : TypeError: Assignment to constant variable.
}
// console.log(message); // Erreur fatale : ReferenceError: message is not defined
```

#### Règle d'or en React :
* Utilisez **`const` par défaut** pour 95% de vos déclarations (composants, fonctions, imports, objets, états dérivés).
* N'utilisez **`let`** que si la variable a vocation à être expressément réassignée (comme les compteurs d'une boucle classique).
* **Bannissez définitivement `var`** de vos projets modernes.

### 3.2 Fonctions fléchées (Arrow Functions) et contexte lexical `this`

Les fonctions fléchées, introduites avec la syntaxe `() => {}`, ne sont pas un simple raccourci d'écriture. Elles modifient fondamentalement la gestion du mot-clé **`this`**.

#### 1. Évolution syntaxique :
```javascript
// Syntaxe traditionnelle
function additionner(a, b) {
    return a + b;
}

// Fonction fléchée avec corps de bloc
const additionnerFlechee = (a, b) => {
    return a + b;
};

// Fonction fléchée concise avec retour implicite (Implicit Return)
const additionnerCourt = (a, b) => a + b;

// Avec un seul paramètre, les parenthèses sont optionnelles :
const doubler = x => x * 2;

// Pour retourner implicitement un objet, entourez-le de parenthèses :
const creerUtilisateur = (id, nom) => ({ id: id, nom: nom });
```

#### 2. La différence cruciale sur `this` :
Dans une fonction JavaScript classique, la valeur de `this` est dynamique : elle dépend de la manière dont la fonction est appelée lors de l'exécution (contexte de l'appelant). 

Dans une **fonction fléchée**, `this` est **lexical** : la fonction ne crée aucun nouveau contexte `this`. Elle hérite automatiquement de la valeur de `this` de la portée parente où elle a été rédigée.

```javascript
// Démonstration du piège de this avec setTimeout :
const compteur = {
    valeur: 0,
    demarrerClassique: function() {
        setTimeout(function() {
            // Ici, this fait référence à l'objet global (Window) ou undefined en strict mode !
            this.valeur++;
            console.log("Classique :", this.valeur); // Affiche NaN !
        }, 500);
    },
    demarrerFlechee: function() {
        setTimeout(() => {
            // La fonction fléchée capture le this de la méthode demarrerFlechee (donc l'objet compteur)
            this.valeur++;
            console.log("Fléchée :", this.valeur); // Affiche 1 !
        }, 500);
    }
};

compteur.demarrerClassique();
compteur.demarrerFlechee();
```

### 3.4 Déstructuration d'objets et de tableaux

La déstructuration est le mécanisme syntaxique le plus omniprésent en React. Elle permet d'extraire des propriétés d'un objet ou des valeurs d'un tableau pour les stocker dans des variables distinctes en une seule ligne.

#### 1. Déstructuration d'Objets :
```javascript
const stagiaire = {
    id: 101,
    nom: "Amine",
    filiere: "Web Full Stack",
    ville: "Rabat"
};

// Extraction directe : les variables créées portent le même nom que les clés :
const { nom, filiere } = stagiaire;
console.log(nom); // "Amine"

// Renommage de variable lors de l'extraction :
const { ville: villeOrigine } = stagiaire;
console.log(villeOrigine); // "Rabat"

// Valeur par défaut en cas de propriété manquante :
const { pays = "Maroc" } = stagiaire;
console.log(pays); // "Maroc"

// Utilisation directe dans les paramètres d'une fonction (Cas typique des PROPS en React) :
function afficherProfil({ nom, filiere }) {
    console.log(`Profil : ${nom} - ${filiere}`);
}
afficherProfil(stagiaire);
```

#### 2. Déstructuration de Tableaux :
Dans un tableau, l'extraction ne se fait pas par nom de propriété mais par **position ordonnée** :
```javascript
const coordonnees = [34.020882, -6.841650];

// Extraction par indice :
const [latitude, longitude] = coordonnees;
console.log(latitude); // 34.020882

// Ignorer un élément avec une virgule vide :
const couleurs = ["rouge", "vert", "bleu", "jaune"];
const [primaire, , secondaire] = couleurs;
console.log(secondaire); // "bleu"

// C'est exactement cette syntaxe qu'utilise le Hook useState de React :
// const [state, setState] = useState(initialValue);
```

### 3.5 Opérateurs Spread et Rest (`...`)

Les trois petits points `...` changent de nom et de comportement selon le contexte où ils sont employés.

#### 1. L'Opérateur Rest (Regroupement) :
Placé dans la déclaration des paramètres d'une fonction ou lors d'une déstructuration, il rassemble les éléments restants au sein d'un tableau ou d'un nouvel objet.
```javascript
// Rest dans les paramètres d'une fonction :
function totaliserAchats(tauxTVA, ...montantsHT) {
    // montantsHT est un véritable tableau contenant tous les arguments passés après le premier
    const sousTotal = montantsHT.reduce((acc, curr) => acc + curr, 0);
    return sousTotal * (1 + tauxTVA);
}
console.log(totaliserAchats(0.20, 100, 200, 300)); // Calcule la TVA sur 600

// Rest lors d'une déstructuration d'objet :
const produit = { id: 1, nom: "Clavier", prix: 250, stock: 15 };
const { id, ...detailsProduit } = produit;
console.log(detailsProduit); // { nom: "Clavier", prix: 250, stock: 15 }
```

#### 2. L'Opérateur Spread (Propagation / Décomposition) :
Placé lors de l'appel d'une fonction ou de la construction d'un nouveau tableau/objet, il "étale" les éléments d'une structure existante dans une nouvelle.
```javascript
// Clonage et fusion de tableaux :
const frontend = ["HTML", "CSS", "JS"];
const backend = ["Node.js", "Express"];
const fullstack = [...frontend, "React", ...backend, "MongoDB"];

// Clonage et mise à jour d'objets (INDISPENSABLE POUR LE STATE REACT) :
const utilisateurInitial = { id: 1, prenom: "Nadia", role: "Stagiaire" };

// On crée une NOUVELLE référence en modifiant ou en ajoutant des propriétés :
const utilisateurMisAJour = {
    ...utilisateurInitial,
    role: "Formatrice",    // Écrase la valeur précédente
    datePromotion: "2026" // Ajoute une nouvelle clé
};
console.log(utilisateurMisAJour);
// { id: 1, prenom: "Nadia", role: "Formatrice", datePromotion: "2026" }
```

### 3.6 Système de modules ES6 (`import` / `export`)

Le standard ES6 formalise le découpage d'un projet en fichiers JavaScript isolés appelés **modules**. Tout ce qui est déclaré dans un module est privé par défaut.

#### 1. Les Exports Nommés (Named Exports) :
Permettent d'exporter plusieurs variables, classes ou fonctions depuis le même fichier :
```javascript
// Dans le fichier utils/math.js :
export const PI = 3.14159;
export function calculerAireCercle(rayon) {
    return PI * rayon * rayon;
}
export function calculerPerimetre(rayon) {
    return 2 * PI * rayon;
}

// Importation ciblée dans app.js :
import { PI, calculerAireCercle } from './utils/math.js';
// Importation avec renommage :
import { calculerAireCercle as aire } from './utils/math.js';
// Importation globale sous un alias :
import * as MathUtils from './utils/math.js';
```

#### 2. L'Export par Défaut (Default Export) :
Chaque fichier ne peut posséder **qu'un seul export par défaut**. C'est la convention standard pour exporter un composant React :
```javascript
// Dans le fichier components/Bouton.js :
const Bouton = () => {
    return "<button>Cliquez ici</button>";
};
export default Bouton;

// Importation dans App.js (sans accolades, le nom d'import peut être librement choisi) :
import Bouton from './components/Bouton.js';
import MonSuperBouton from './components/Bouton.js'; // Fonctionne également !
```

### 3.7 Callbacks et programmation événementielle

Un **callback** (ou fonction de rappel) est une fonction passée en argument à une autre fonction, afin d'être exécutée ultérieurement lorsque survient un événement spécifique ou lorsqu'un traitement asynchrone est achevé.

```javascript
// Traitement de collections avec callbacks :
const notes = [12, 18, 9, 15, 7];

// Utilisation de callbacks avec .filter() et .map()
const notesValidees = notes
    .filter(note => note >= 10) // Callback retournant un booléen
    .map(note => note + 1);     // Callback retournant une transformation

console.log(notesValidees); // [13, 19, 16]
```
En React, les callbacks constituent le moyen canonique pour un **composant enfant d'envoyer des informations vers son parent** (ex: `onChange`, `onDeleteTask`).

### 3.8 Immutabilité des données et stratégies de copie (Shallow vs Deep Copy)

La compréhension de la gestion de la mémoire est le prérequis technique numéro un pour manipuler le State dans React et Redux.

#### 1. Mémoire : Stack (Pile) vs Heap (Tas)
* Les **types primitifs** (nombres, chaînes, booléens, null, undefined) sont stockés par valeur dans la Stack.
* Les **types références** (Objets, Tableaux, Fonctions) ont leurs données stockées dans le Heap ; la variable ne contient qu'une simple **adresse mémoire (pointeur)** vers cet emplacement.

```javascript
// Piège classique de la copie par référence :
const userA = { nom: "Karim", age: 25 };
const userB = userA; // ATTENTION : On copie uniquement le pointeur d'adresse mémoire !

userB.age = 26; // Modifie l'unique objet dans le Heap
console.log(userA.age); // Affiche 26 ! userA a été altéré involontairement.
```

#### 2. Shallow Copy (Copie Superficielle) :
Une copie superficielle génère un nouvel objet/tableau pour le premier niveau de clés, mais **conserve les références d'origine pour les objets ou tableaux imbriqués**.
```javascript
const article = {
    titre: "Guide React",
    prix: 150,
    auteur: { nom: "Imane", role: "Formatrice" } // Objet imbriqué
};

// Copie superficielle via Spread operator :
const copieSuperficielle = { ...article };
copieSuperficielle.prix = 180; // OK : n'affecte pas l'objet article

// MAIS pour les objets imbriqués :
copieSuperficielle.auteur.nom = "Yassine"; 
console.log(article.auteur.nom); // Affiche "Yassine" ! La référence imbriquée a été partagée.
```

#### 3. Deep Copy (Copie Profonde) :
Une copie profonde duplique l'intégralité de l'arborescence, rompant tout lien mémoire avec l'original.
```javascript
// Solution moderne native en JavaScript (Node 17+ et navigateurs modernes) :
const copieProfonde = structuredClone(article);

// Ancienne astuce (comporte des limites avec les fonctions ou dates) :
const copieViaJSON = JSON.parse(JSON.stringify(article));

copieProfonde.auteur.nom = "Zineb";
console.log(article.auteur.nom); // Reste "Yassine", l'isolation est 100% totale !
```

> **Pourquoi React exige l'immutabilité ?**
> React optimise ses performances en effectuant une comparaison de surface (*Shallow Comparison* : `oldState === newState`). Si vous modifiez directement l'intérieur d'un objet (`state.valeur = 10`), la référence mémoire de l'objet ne change pas. React considère alors que rien n'a bougé et **refuse de déclencher le re-rendu de votre composant** !

### 3.9 Asynchronisme : Event Loop, Promesses, async/await et Fetch API

JavaScript est un langage **monothreadé** (un seul fil d'exécution principal). Pour exécuter des opérations longues (requêtes réseau, délais) sans geler l'interface graphique, il s'appuie sur le mécanisme de l'**Event Loop**.

#### 1. Les Promesses (Promises) :
Une `Promise` est un objet représentant l'état futur d'une opération asynchrone.
Elle possède 3 états exclusifs :
* `pending` (en attente d'achèvement)
* `fulfilled` (résolue avec succès, délivre une valeur via `.then()`)
* `rejected` (échouée, délivre une erreur via `.catch()`)

```javascript
// Création d'une promesse personnalisée :
function verifierStock(produitId) {
    return new Promise((resolve, reject) => {
        setTimeout(() => {
            if (produitId > 0) {
                resolve({ id: produitId, disponible: true, quantite: 5 });
            } else {
                reject(new Error("Identifiant de produit invalide."));
            }
        }, 800);
    });
}

// Consommation avec .then() et .catch() :
verifierStock(10)
    .then(data => console.log("Stock disponible :", data))
    .catch(err => console.error("Erreur détectée :", err.message))
    .finally(() => console.log("Opération terminée."));
```

#### 2. La Révolution `async` / `await` :
Introduits en ES2017, les mots-clés `async` et `await` permettent de rédiger du code asynchrone qui se lit comme du code séquentiel synchrone, éliminant les pyramides de `.then()` imbriqués.

Règles fondamentales :
* Le mot-clé `await` ne peut être utilisé qu'à l'intérieur d'une fonction précédée de `async`.
* Une fonction `async` retourne systématiquement une Promesse.
* Les erreurs sont interceptées naturellement avec des blocs classiques `try { ... } catch (error) { ... }`.

```javascript
// Exemple de requête HTTP moderne avec Fetch et async/await :
async function chargerUtilisateurs() {
    try {
        console.log("Début du chargement...");
        const response = await fetch("https://jsonplaceholder.typicode.com/users");
        
        // Toujours vérifier si le serveur a répondu avec un statut 200-299 :
        if (!response.ok) {
            throw new Error(`Erreur serveur HTTP : ${response.status}`);
        }
        
        const utilisateurs = await response.json(); // Conversion du flux JSON en objet JS
        console.log("Liste des utilisateurs chargés :", utilisateurs);
        return utilisateurs;
    } catch (erreur) {
        console.error("Échec de la requête réseau :", erreur.message);
    }
}
```

### 4.1 Histoire, philosophie et caractéristiques de React
Créée par Jordan Walke, ingénieur chez Meta (Facebook), et déployée en open-source en mai 2013, **React** est une bibliothèque JavaScript déclarative, efficace et flexible dédiée à la conception d'interfaces utilisateur (UI).

#### Piliers philosophiques :
1. **Déclaratif plutôt qu'impératif** :
   * *Approche impérative (Vanilla JS)* : Le développeur décrit manuellement chaque étape de mutation (`var p = document.createElement('p'); p.textContent = 'Salut'; div.appendChild(p);`).
   * *Approche déclarative (React)* : Le développeur décrit simplement l'état final désiré (`return <p>Salut</p>;`). React se charge d'aligner automatiquement le DOM avec cet état.
2. **Architecture à base de composants** : L'interface est découpée en blocs autonomes, encapsulés et réutilisables qui gèrent leur propre état.
3. **Apprendre une fois, écrire partout** : Les mêmes concepts s'appliquent sur le web (React DOM), sur mobile (React Native) ou pour des applications desktop (Electron).

---

### 4.2 Le Virtual DOM (DOM Virtuel) et l'algorithme de réconciliation

La manipulation directe du DOM du navigateur est notoirement lente. À chaque fois qu'un nœud est altéré, le navigateur doit recalculer l'arborescence géométrique de toute la page.

React résout ce goulet d'étranglement grâce au **Virtual DOM** :
1. **Représentation mémoire** : Le DOM Virtuel est un arbre d'objets JavaScript légers qui reproduit fidèlement la structure du DOM réel.
2. **Phase de Render** : Lorsque le state d'un composant change, React génère un nouvel arbre Virtual DOM complet représentant la nouvelle version de l'UI.
3. **Algorithme de Diffing** : React compare instantanément ce nouvel arbre avec l'ancien arbre en mémoire afin d'identifier les seules différences réelles.
4. **Réconciliation et Batching** : React applique de manière groupée (*batch update*) uniquement les mutations strictement indispensables sur le DOM réel du navigateur.

```
       State change
            │
            ▼
    [Nouvel arbre VDOM]  <─── Comparaison (Diffing) ───>  [Ancien arbre VDOM]
            │
            ▼
   Calcul des différences minimales
            │
            ▼
    [DOM Réel mis à jour uniquement sur les nœuds modifiés] (Rapide !)
```

### 5.2 Syntaxe JSX en profondeur et transpilation Babel

**JSX** signifie **JavaScript XML**. C'est une extension de syntaxe permettant d'écrire des structures semblables à du HTML directement au sein d'un script JavaScript.

#### 1. Rôle du transpileur Babel :
Les navigateurs web ne comprennent pas nativement JSX. L'outil **Babel** intervient lors de la compilation pour traduire chaque balise JSX en un appel JavaScript standard à la méthode `React.createElement()` :

```javascript
// Ce que vous écrivez en JSX :
const element = <h1 className="titre">Bienvenue sur React</h1>;

// Ce que Babel produit en JavaScript pur :
const element = React.createElement(
  'h1',
  { className: 'titre' },
  'Bienvenue sur React'
);
```

#### 2. Règles syntaxiques impératives de JSX :
1. **Un seul élément racine parent** : Tout composant doit retourner une unique balise conteneur parente. Pour éviter d'ajouter des balises `<div>` inutiles dans le DOM, on utilise un **Fragment** :
   ```jsx
   // Correct avec Fragment raccourci :
   return (
     <>
       <h1>Titre</h1>
       <p>Paragraphe</p>
     </>
   );
   ```
2. **Fermeture obligatoire de toutes les balises** : Les balises orphelines comme `<img>`, `<input>`, `<br>` doivent impérativement être auto-fermantes (`<img src="..." alt="..." />`, `<input type="text" />`).
3. **Attributs en camelCase** :
   * `class` devient `className` (car `class` est un mot réservé en JavaScript).
   * `for` devient `htmlFor`.
   * `tabindex` devient `tabIndex`.
4. **Injection d'expressions JavaScript entre accolades `{}`** : Tout code JS valide produisant une valeur peut être inséré :
   ```jsx
   const age = 20;
   return <div>Âge : {age} ans ({age >= 18 ? "Majeur" : "Mineur"})</div>;
   ```

### 5.3 Types de composants : Fonctionnels vs Classes

#### 1. Composants Fonctionnels (La norme moderne) :
Une simple fonction JavaScript qui reçoit les `props` en argument et renvoie du JSX.
```jsx
// Composant fonctionnel moderne :
const CarteUtilisateur = ({ nom, role }) => {
    return (
        <div className="carte">
            <h2>{nom}</h2>
            <p>Rôle : {role}</p>
        </div>
    );
};
export default CarteUtilisateur;
```

#### 2. Composants de Classe (Héritage historique) :
Une classe ES6 qui hérite de `React.Component` et implémente obligatoirement la méthode `render()`.
```jsx
import React, { Component } from 'react';

class CarteUtilisateurClass extends Component {
    render() {
        // Les props sont accessibles via this.props
        const { nom, role } = this.props;
        return (
            <div className="carte">
                <h2>{nom}</h2>
                <p>Rôle : {role}</p>
            </div>
        );
    }
}
export default CarteUtilisateurClass;
```

### 5.4 Manipulation des Propriétés (Props) et composition

Les **props** (propriétés) sont les paramètres d'entrée d'un composant. Elles permettent à un composant parent de transmettre des données à ses composants enfants.

#### Caractéristiques des Props :
* **Unidirectionnelles** : Les props circulent exclusivement du haut vers le bas (Parent $ightarrow$ Enfant).
* **Strictement Immuables (Lecture seule)** : Un composant enfant **ne doit jamais modifier ses propres props**. Toute fonction React doit agir comme une fonction pure vis-à-vis de ses props.

#### Utilisation avancée de `props.children` :
`children` est une prop spéciale qui contient les éléments placés entre la balise d'ouverture et de fermeture d'un composant :
```jsx
// Composant conteneur générique :
const Encadre = ({ titre, children }) => {
    return (
        <div className="boite-style">
            <h3>{titre}</h3>
            <div className="contenu">{children}</div>
        </div>
    );
};

// Utilisation :
<Encadre titre="Informations Étudiant">
    <p>Sara Alami</p>
    <p>Filière Full Stack</p>
</Encadre>
```

### 5.5 Communication inter-composants

Il existe 3 schémas de communication classiques dans React :

#### 1. Parent vers Enfant :
S'effectue directement par les props :
```jsx
// Le parent envoie la donnée :
<Produit nom="Ordinateur Portable" prix={8500} />
```

#### 2. Enfant vers Parent :
Un enfant ne peut pas injecter directement de props dans son parent. Il utilise le mécanisme d'une **fonction de rappel (callback)** fournie par le parent via les props :
```jsx
// Parent.js
const Parent = () => {
    const recevoirMessage = (texte) => {
        console.log("Message reçu de l'enfant :", texte);
    };

    return <Enfant onEnvoyer={recevoirMessage} />;
};

// Enfant.js
const Enfant = ({ onEnvoyer }) => {
    return (
        <button onClick={() => onEnvoyer("Bonjour depuis l'enfant !")}>
            Notifier le Parent
        </button>
    );
};
```

#### 3. Entre Composants Frères (Siblings) : Remontée d'État (Lifting State Up) :
Deux composants frères ne peuvent pas dialoguer directement. La solution consiste à **déplacer l'état dans leur parent commun le plus proche**. Le parent gère la variable d'état, la transmet au premier frère par props, et transmet la fonction de mise à jour au second frère.

### 5.6 Gestion des événements (SyntheticEvents)

React utilise son propre système d'événements appelé **SyntheticEvent**. C'est une surcouche multi-navigateurs qui englobe les événements natifs du navigateur pour garantir un comportement 100% identique sur Chrome, Firefox, Safari et Edge.

#### Bonnes pratiques d'écriture :
```jsx
const FormulaireContact = () => {
    const handleClick = (e) => {
        console.log("Type d'événement :", e.type); // "click"
    };

    const handleParametre = (id, e) => {
        console.log("ID sélectionné :", id);
    };

    return (
        <div>
            {/* Gestionnaire sans paramètre (on passe la référence de la fonction) */}
            <button onClick={handleClick}>Bouton 1</button>

            {/* Gestionnaire avec paramètre (on utilise une fonction fléchée anonyme) */}
            <button onClick={(e) => handleParametre(42, e)}>Bouton 2</button>
        </div>
    );
};
```

### 5.7 Gestion d'état local (State) : Classes vs Hook `useState`

Alors que les props permettent de configurer un composant depuis l'extérieur, le **State** représente la mémoire interne et vivante du composant. Lorsque le state change, **le composant se re-rend automatiquement**.

#### 1. Le State dans les Composants de Classe :
Initialisé dans le constructeur via `this.state`, mis à jour obligatoirement avec la méthode `this.setState()`.
```jsx
class CompteurClass extends React.Component {
    constructor(props) {
        super(props);
        this.state = { compteur: 0 };
        // Nécessité de lier manuellement this dans le constructeur :
        this.incrementer = this.incrementer.bind(this);
    }

    incrementer() {
        this.setState(prevState => ({ compteur: prevState.compteur + 1 }));
    }

    render() {
        return (
            <div>
                <p>Valeur : {this.state.compteur}</p>
                <button onClick={this.incrementer}>Incrémenter</button>
            </div>
        );
    }
}
```

#### 2. Le State dans les Composants Fonctionnels avec le Hook `useState` :
Introduit avec React 16.8, le hook `useState` simplifie radicalement cette gestion :
```jsx
import React, { useState } from 'react';

const Compteur = () => {
    // useState renvoie un tableau contenant : [valeurActuelle, fonctionDeMiseAJour]
    const [compteur, setCompteur] = useState(0);

    return (
        <div>
            <p>Valeur : {compteur}</p>
            <button onClick={() => setCompteur(prev => prev + 1)}>
                Incrémenter
            </button>
        </div>
    );
};
```

---

### 5.8 Les 4 règles cardinales du State dans React

1. **Le State est Asynchrone** : Appeler `setCompteur(compteur + 1)` ne modifie pas la variable `compteur` immédiatement sur la ligne suivante. React planifie la mise à jour pour le prochain cycle de rendu.
2. **Le State déclenche le re-rendu** : Toute modification effectuée via la fonction `set...` déclenche un nouvel appel du composant fonctionnel et recalcule le Virtual DOM.
3. **Le State est strictement isolé** : Si vous affichez 10 fois le composant `<Compteur />`, chaque instance dispose de son propre état indépendant en mémoire.
4. **Le State doit être traité comme immuable** : Ne modifiez jamais directement un état contenant un objet ou un tableau (`tableau.push(x)` est proscrit ; utilisez `setTableau([...tableau, x])`).

### 5.9 Exercices pratiques résolus du Module 4

#### Exercice : Gestionnaire de Tâches Interactif (TaskManager)
**Objectif** : Créer un composant permettant d'afficher une liste de tâches, de basculer leur statut (terminé/non terminé) et d'ajouter de nouvelles tâches.

```jsx
import React, { useState } from 'react';

const TaskManager = () => {
    const [tasks, setTasks] = useState([
        { id: 1, title: "Apprendre JSX", done: true },
        { id: 2, title: "Maîtriser useState", done: false }
    ]);
    const [newTitle, setNewTitle] = useState("");

    const toggleTask = (id) => {
        setTasks(tasks.map(task => 
            task.id === id ? { ...task, done: !task.done } : task
        ));
    };

    const addTask = (e) => {
        e.preventDefault();
        if (!newTitle.trim()) return;
        const newTask = {
            id: Date.now(),
            title: newTitle,
            done: false
        };
        setTasks([...tasks, newTask]);
        setNewTitle("");
    };

    return (
        <div style={{ padding: '20px', maxWidth: '400px' }}>
            <h2>Mes Tâches</h2>
            <form onSubmit={addTask}>
                <input 
                    type="text" 
                    value={newTitle} 
                    onChange={(e) => setNewTitle(e.target.value)} 
                    placeholder="Nouvelle tâche..."
                />
                <button type="submit">Ajouter</button>
            </form>
            <ul>
                {tasks.map(task => (
                    <li key={task.id} style={{ textDecoration: task.done ? 'line-through' : 'none' }}>
                        <span>{task.title}</span>
                        <button onClick={() => toggleTask(task.id)}>
                            {task.done ? "Annuler" : "Terminer"}
                        </button>
                    </li>
                ))}
            </ul>
        </div>
    );
};

export default TaskManager;
```

### 6.1 Stratégies de stylisation

Il existe 4 approches majeures pour styliser une application React :

#### 1. Styles Inline (en ligne) :
Définis via un objet JavaScript passé à la prop `style`. Les propriétés CSS s'écrivent en `camelCase` :
```jsx
const styleTitre = {
    color: '#0066cc',
    fontSize: '24px',
    backgroundColor: '#f0f0f0',
    padding: '10px'
};
<h1 style={styleTitre}>Titre Stylisé</h1>
```
*Inconvénients* : Pas de pseudo-classes (`:hover`, `:focus`), pas de media queries, code lourd et non réutilisable à grande échelle.

#### 2. Fichiers CSS traditionnels :
Fichier `.css` normal importé via `import './Bouton.css';`.
*Inconvénient majeur* : **Les styles sont globaux**. Une classe `.bouton` stylisera tous les éléments de l'application ayant cette classe, créant des collisions de style imprévues.

#### 3. CSS Modules (Recommandé) :
Fichier nommé `Composant.module.css`. Webpack transforme automatiquement les noms de classes lors du build en identifiants uniques hachés (ex: `Bouton_btn__3a8f1`).
```css
/* Bouton.module.css */
.boutonPrimaire {
    background-color: blue;
    color: white;
}
```
```jsx
// Bouton.js
import styles from './Bouton.module.css';

const Bouton = () => {
    return <button className={styles.boutonPrimaire}>Valider</button>;
};
```

#### 4. Styled Components (CSS-in-JS) :
Utilisation de la bibliothèque `styled-components` pour générer des composants stylisés avec gestion des props :
```jsx
import styled from 'styled-components';

const BoutonDynamique = styled.button`
    background-color: ${props => props.primaire ? 'blue' : 'gray'};
    color: white;
    padding: 10px 20px;
    border-radius: 4px;
`;
```

### 6.2 Organisation et utilisation des Assets (dossier `src` vs `public`)

| Critère | Dossier `src/assets/` | Dossier `public/` |
| :--- | :--- | :--- |
| **Méthode d'accès** | Importation JavaScript : `import logo from './logo.svg';` | Chemin URL absolu : `<img src="/logo.svg" />` |
| **Vérification compilation** | **Oui** (Si le fichier est déplacé ou manquant, la compilation échoue immédiatement) | **Non** (Si l'image manque, elle se brise silencieusement dans le navigateur avec une 404) |
| **Optimisation Webpack** | **Oui** (Minification, ajout de hashes uniques dans le nom pour invalider le cache) | **Non** (Servi tel quel, sans traitement) |
| **Cas d'usage** | Images de composants, logos, icônes, SVG | `favicon.ico`, `manifest.json`, fichiers téléchargés dynamiquement |

### 6.3 Rendu de listes et importance cruciale des Clés (`key`)

Le rendu dynamique de collections s'effectue grâce à la méthode native JavaScript `.map()` :

```jsx
const etudiants = [
    { id: 'e1', nom: 'Yassine' },
    { id: 'e2', nom: 'Mounir' },
    { id: 'e3', nom: 'Salma' }
];

return (
    <ul>
        {etudiants.map(etudiant => (
            <li key={etudiant.id}>{etudiant.nom}</li>
        ))}
    </ul>
);
```

> **Pourquoi la prop `key` est-elle vitale ?**
> La clé permet à l'algorithme de réconciliation de React d'identifier de manière unique chaque élément entre deux rendus. Si vous insérez, supprimez ou réordonnez un élément, React utilise la `key` pour ne mettre à jour que le nœud concerné.
> **Règle absolue** : N'utilisez **jamais l'index du tableau** (`(item, index) => <li key={index}>`) comme clé si la liste peut être filtrée, triée ou modifiée, car cela perturbe l'état interne des composants et détériore les performances.

### 6.4 Affichage conditionnel
React supporte trois mécanismes pour masquer ou afficher des éléments :

1. **L'opérateur ternaire `condition ? <A /> : <B />`** : Idéal pour basculer entre deux rendus alternatifs.
2. **L'opérateur logique `&&` (Court-circuit)** : Idéal pour afficher un composant uniquement si une condition est vraie :
   ```jsx
   {estConnecte && <BoutonDeconnexion />}
   ```
   *Attention au piège* : Si votre condition vaut `0` (ex: `tableau.length && <List />`), React affichera le chiffre `0` à l'écran. Utilisez `tableau.length > 0 && <List />`.
3. **Le bloc `if/else` classique** : Hors du JSX, pour retourner des vues complètes distinctes (ex: écran de chargement).

### 6.5 Formulaires contrôlés (Controlled Components)
Dans un formulaire contrôlé, la balise HTML (`<input>`, `<textarea>`, `<select>`) ne stocke pas sa propre valeur en interne dans le DOM. C'est l'état React qui constitue **l'unique source de vérité** :

```jsx
import React, { useState } from 'react';

const FormulaireInscription = () => {
    const [formData, setFormData] = useState({
        nom: '',
        email: '',
        ville: 'Casablanca'
    });

    const handleChange = (e) => {
        const { name, value } = e.target;
        setFormData(prev => ({
            ...prev,
            [name]: value // Mise à jour dynamique de la propriété correspondante
        }));
    };

    const handleSubmit = (e) => {
        e.preventDefault(); // Empêche le rechargement brutal de la page
        console.log("Données envoyées :", formData);
    };

    return (
        <form onSubmit={handleSubmit}>
            <input 
                type="text" 
                name="nom" 
                value={formData.nom} 
                onChange={handleChange} 
                placeholder="Nom complet" 
            />
            <input 
                type="email" 
                name="email" 
                value={formData.email} 
                onChange={handleChange} 
                placeholder="Adresse email" 
            />
            <select name="ville" value={formData.ville} onChange={handleChange}>
                <option value="Casablanca">Casablanca</option>
                <option value="Rabat">Rabat</option>
                <option value="Tanger">Tanger</option>
            </select>
            <button type="submit">S'inscrire</button>
        </form>
    );
};
```

### 6.6 Effets de bord avec le Hook `useEffect`

Un **effet de bord (Side Effect)** est toute opération qui interagit avec le monde extérieur au composant : effectuer des requêtes HTTP distantes, s'abonner à un écouteur d'événement global, manipuler directement le titre de la page HTML (`document.title`), configurer un minuteur (`setInterval`).

#### Les 3 variantes du tableau de dépendances :
```jsx
// 1. Sans tableau de dépendances : S'exécute après CHAQUE rendu (Rarement souhaité)
useEffect(() => {
    console.log("Rendu exécuté");
});

// 2. Avec un tableau de dépendances VIDE [] :
// S'exécute UNIQUEMENT au montage du composant (équivalent componentDidMount)
useEffect(() => {
    console.log("Composant monté à l'écran");
}, []);

// 3. Avec des dépendances [valeurA, valeurB] :
// S'exécute au montage, puis se ré-exécute uniquement si valeurA ou valeurB change
useEffect(() => {
    console.log("Valeur A a été modifiée :", valeurA);
}, [valeurA]);

// 4. Avec fonction de nettoyage (Cleanup Function) :
// S'exécute lors du démontage du composant (équivalent componentWillUnmount)
useEffect(() => {
    const timer = setInterval(() => console.log("Tick"), 1000);
    return () => {
        clearInterval(timer); // Nettoie le timer pour éviter les fuites mémoire
    };
}, []);
```

### 6.7 Consommation d'APIs distantes (Fetch API et Axios)

Modèle complet de gestion d'un appel réseau intégrant les 3 états d'interface (**Chargement**, **Erreur**, **Succès**) :

```jsx
import React, { useState, useEffect } from 'react';
import axios from 'axios';

const ListeArticles = () => {
    const [articles, setArticles] = useState([]);
    const [chargement, setChargement] = useState(true);
    const [erreur, setErreur] = useState(null);

    useEffect(() => {
        const recupererArticles = async () => {
            try {
                setChargement(true);
                // Axios gère automatiquement la sérialisation et le parsing JSON
                const response = await axios.get("https://jsonplaceholder.typicode.com/posts?_limit=5");
                setArticles(response.data);
                setErreur(null);
            } catch (err) {
                setErreur("Impossible de charger les articles. Vérifiez votre connexion.");
            } finally {
                setChargement(false);
            }
        };

        recupererArticles();
    }, []);

    if (chargement) return <p>Chargement des données en cours...</p>;
    if (erreur) return <p style={{ color: 'red' }}>{erreur}</p>;

    return (
        <div>
            <h2>Articles Récents</h2>
            {articles.map(article => (
                <div key={article.id} style={{ borderBottom: '1px solid #ccc', margin: '10px 0' }}>
                    <h4>{article.title}</h4>
                    <p>{article.body}</p>
                </div>
            ))}
        </div>
    );
};
```

## 7. MODULE 6 (PDF 6) : ROUTAGE SPA & TESTS AUTOMATISÉS

### 7.1 Routage d'application avec React Router DOM v6
Dans une SPA, le routage permet de synchroniser l'affichage des composants avec l'URL présente dans la barre d'adresses du navigateur, sans provoquer le rechargement de la page HTML.

Installation :
```bash
npm install react-router-dom
```

---

### 7.2 Composants fondamentaux et architecture

1. `<BrowserRouter>` : Composant racine qui écoute les changements d'URL via l'API History du navigateur.
2. `<Routes>` : Conteneur qui analyse l'URL actuelle et affiche le premier composant `<Route>` dont le chemin correspond.
3. `<Route>` : Associe une chaîne de chemin (`path`) à un composant React (`element`).
4. `<Link>` et `<NavLink>` : Remplacent la balise `<a href="...">` pour naviguer sans recharger. `<NavLink>` injecte automatiquement une classe `active` sur le lien correspondant à la page en cours.

```jsx
// App.js
import React from 'react';
import { BrowserRouter, Routes, Route, NavLink } from 'react-router-dom';
import Accueil from './pages/Accueil';
import APropos from './pages/APropos';
import Contact from './pages/Contact';
import NonTrouve from './pages/NonTrouve';

function App() {
    return (
        <BrowserRouter>
            <nav style={{ display: 'flex', gap: '15px', padding: '10px' }}>
                <NavLink to="/" end>Accueil</NavLink>
                <NavLink to="/a-propos">À Propos</NavLink>
                <NavLink to="/contact">Contact</NavLink>
            </nav>

            <Routes>
                <Route path="/" element={<Accueil />} />
                <Route path="/a-propos" element={<APropos />} />
                <Route path="/contact" element={<Contact />} />
                {/* Route générique 404 */}
                <Route path="*" element={<NonTrouve />} />
            </Routes>
        </BrowserRouter>
    );
}
```

### 7.5 Tests automatisés : Jest et React Testing Library (RTL)

Tester son code permet d'assurer la **non-régression** lors de l'ajout de fonctionnalités.

* **Jest** : Le framework d'exécution de tests (lance les suites de tests, fournit `describe()`, `test()`, `expect()`).
* **React Testing Library** : Fournit des utilitaires pour monter les composants en mémoire et interagir avec eux en se plaçant du point de vue de l'utilisateur final (recherche de textes, clics de boutons).

```jsx
// Compteur.js
import React, { useState } from 'react';
```

## 8. MODULE 7 (PDF 7) : EXPLOITER REDUX AVEC REACT JS (CORE REDUX)

### 8.1 Limites du state local et problématique du Prop Drilling

Dans une application React complexe (ex: E-commerce), de nombreux composants dispersés ont besoin de partager les mêmes données (ex: l'utilisateur connecté, le contenu du panier, le thème graphique sombre/clair).

Avec le seul state local de React, le développeur est contraint de faire descendre les props manuellement à travers 5 ou 10 composants intermédiaires qui n'en ont pourtant pas l'utilité : c'est le syndrome du **Prop Drilling**.

```
PROBLÈME : PROP DRILLING                      SOLUTION : STORE GLOBAL REDUX
      <App /> (State du panier)                     <Store Redux Global>
         │                                              ▲           ▲
         ▼                                              │           │
     <Header /> (Ne sert à rien)                        │           │
         │                                   useSelector()   useDispatch()
         ▼                                              │           │
     <Nav /> (Ne sert à rien)                           ▼           │
         │                                         <Header />   <ProductCard />
         ▼
     <CartWidget /> (Utilise le panier !)
```

---

### 8.2 Concepts fondateurs de Redux

Redux repose sur **3 principes fondamentaux** :
1. **Unique source de vérité** : Tout l'état global de l'application est stocké dans un objet JavaScript unique au sein d'un seul **Store**.
2. **L'état est en lecture seule** : La seule façon de modifier le state est d'émettre une **Action** (un objet décrivant ce qui s'est passé).
3. **Les modifications sont faites par des fonctions pures** : Pour spécifier comment le state change en réponse à une action, on écrit des **Reducers** (fonctions pures sans effets secondaires).

```
FLUX DE DONNÉES UNIDIRECTIONNEL REDUX :

  [Composant UI] ──── dispatch(action) ────> [ Reducer ]
        ▲                                          │
        │                                          │ (Calcule le nouveau state)
        │                                          ▼
  Re-rendu automatique <────── Notifié ───── [ Store Global ]
```

---

### 8.3 Anatomie du Core Redux : Action, Reducer et Store

#### 1. L'Action :
Un simple objet JavaScript qui décrit l'intention. Possède obligatoirement une propriété `type` :
```javascript
const actionAjouter = {
    type: 'CART_ADD_ITEM',
    payload: { id: 101, nom: "Souris Sans Fil", prix: 150 }
};
```

#### 2. Le Reducer :
Une fonction pure `(state, action) => newState`. Si l'action ne le concerne pas, il doit impérativement renvoyer le state actuel inchangé :
```javascript
const etatInitial = {
    articles: [],
    total: 0
};

function panierReducer(state = etatInitial, action) {
    switch (action.type) {
        case 'CART_ADD_ITEM':
            return {
                ...state,
                articles: [...state.articles, action.payload],
                total: state.total + action.payload.prix
            };
        case 'CART_CLEAR':
            return etatInitial;
        default:
            return state;
    }
}
```

### 8.4 Intégration React-Redux : `Provider`, `useSelector`, `useDispatch`

Installation des deux bibliothèques nécessaires :
```bash
npm install redux react-redux
```

#### 1. Distribution du Store via `<Provider>` dans `index.js` :
```jsx
import React from 'react';
import ReactDOM from 'react-dom/client';
import { createStore } from 'redux';
import { Provider } from 'react-redux';
import panierReducer from './redux/panierReducer';

root.render(

    </Provider>

```

#### 2. Consommation dans les composants avec `useSelector` et `useDispatch` :
```jsx
import React from 'react';
import { useSelector, useDispatch } from 'react-redux';

const PanierWidget = () => {

    const total = useSelector(state => state.total);
    const nombreArticles = useSelector(state => state.articles.length);

    // useDispatch permet d'émettre des actions vers le store :

        <div style={{ padding: '10px', border: '1px solid black' }}>
            <h3>Panier ({nombreArticles} articles)</h3>
            <p>Total : {total} DH</p>
            <button onClick={() => dispatch({ type: 'CART_CLEAR' })}>
                Vider le Panier
            </button>
        </div>
    );
};
```

### 8.5 Immutabilité assistée avec la bibliothèque Immer

Dans un reducer Redux traditionnel, mettre à jour des tableaux ou objets imbriqués devient extrêmement lourd à cause de la cascade de spread operators `...`.

La bibliothèque **Immer** résout ce problème grâce à sa fonction `produce(state, draft => { ... })`. Vous modifiez l'argument temporaire `draft` comme s'il s'agissait d'un objet ordinaire modifiable, et Immer produit en arrière-plan une copie immuable parfaite :

```javascript
import { produce } from 'immer';

// SANS IMMER (Complexe et verbeux) :
case 'UPDATE_COMMENT':
    return {
        ...state,
        posts: state.posts.map(post => {
            if (post.id !== action.postId) return post;
            return {
                ...post,
                comments: post.comments.map(c => c.id === action.commentId ? { ...c, text: action.newText } : c)
            };
        })
    };

// AVEC IMMER (Lisible et direct) :
case 'UPDATE_COMMENT':
    return produce(state, draft => {
        const post = draft.posts.find(p => p.id === action.postId);
        const comment = post.comments.find(c => c.id === action.commentId);
        comment.text = action.newText; // Mutation directe autorisée sur le draft !
    });
```

### 8.6 Conception et utilisation des Sélecteurs (Selectors)

Un sélecteur est une fonction pure qui encapsule la logique d'extraction ou de calcul d'une information à partir du state global :

```javascript
// Définis dans un fichier selectors/panierSelectors.js :
export const selectArticlesDuPanier = state => state.articles;
export const selectNombreArticles = state => state.articles.length;
export const selectMontantTotalTTC = state => state.articles.reduce((acc, a) => acc + (a.prix * 1.2), 0);

// Dans le composant :
const totalTTC = useSelector(selectMontantTotalTTC);
```

## 9. MODULE 8 (PDF 8) : MANIPULER LES FONCTIONNALITÉS AVANCÉES DE REDUX & REDUX TOOLKIT

### 9.1 Découpage et combinaison des reducers (`combineReducers`)

Dans une application d'entreprise réelle, avoir un unique fichier reducer pour tout le site mène à un script illisible de 1500 lignes. La bonne pratique consiste à créer **un reducer par domaine métier** et à les assembler avec `combineReducers` :

```javascript
import { createStore, combineReducers } from 'redux';
import authReducer from './features/auth/authReducer';
import productReducer from './features/products/productReducer';
import cartReducer from './features/cart/cartReducer';

// Assemblage des sous-états dans le store global :
const rootReducer = combineReducers({
    auth: authReducer,       // Accessible via state.auth
    products: productReducer,// Accessible via state.products
    cart: cartReducer        // Accessible via state.cart
});

export const store = createStore(rootReducer);
```

---

### 9.2 Pattern standard de communication avec les APIs distantes

> **Règle fondamentale absolue** : Un Reducer doit rester une fonction **pure et 100% synchrone**. Il est formellement interdit d'exécuter un appel `fetch()` ou `axios` à l'intérieur d'un reducer.

Le standard de l'industrie pour gérer une requête asynchrone repose sur le cycle des **3 actions** :
1. `FETCH_START` (ou `PENDING`) : Déclenchée avant l'appel API $ightarrow$ positionne `loading: true`, `error: null`.
2. `FETCH_SUCCESS` : Déclenchée si l'API répond $ightarrow$ stocke les données dans `data: action.payload`, `loading: false`.
3. `FETCH_ERROR` : Déclenchée si la requête échoue $ightarrow$ stocke l'erreur dans `error: action.payload`, `loading: false`.

### 9.3 Révolution Redux Toolkit (RTK) : `configureStore`, `createSlice`

Redux classique fonctionnait mais souffrait d'un reproche unanime : il nécessitait trop de "boilerplate" (fichiers constants de types d'actions séparés, action creators séparés, reducers avec de longs blocs `switch`).

L'équipe officielle de Redux a donc créé **Redux Toolkit (RTK)**, qui est désormais la **seule façon recommandée d'écrire du code Redux moderne**.

Installation :
```bash
npm install @reduxjs/toolkit react-redux
```

#### Définition d'un Slice avec `createSlice` :
Un **Slice** rassemble en un seul endroit : le nom, le state initial et les reducers. De plus, Immer est activé nativement, vous pouvez donc modifier directement l'état !

```javascript
// src/features/counter/counterSlice.js
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
    name: 'counter',
    initialState: { valeur: 0 },
    reducers: {
        incrementer: (state) => {
            state.valeur += 1; // Syntaxe mutative autorisée grâce à Immer !
        },
        decrementer: (state) => {
            state.valeur -= 1;
        },
        ajouterValeur: (state, action) => {
            state.valeur += action.payload;
        }
    }
});

// Export automatique des Action Creators générés :
export const { incrementer, decrementer, ajouterValeur } = counterSlice.actions;

// Export du reducer pour le store :
export default counterSlice.reducer;
```

#### Configuration du Store avec `configureStore` :
Remplace avantageusement `createStore()`. Il active automatiquement les DevTools Redux et inclut le middleware Thunk par défaut :

```javascript
// src/app/store.js
import { configureStore } from '@reduxjs/toolkit';
import counterReducer from '../features/counter/counterSlice';

export const store = configureStore({
    reducer: {
        counter: counterReducer
    }
});
```

### 9.4 Système de Middlewares : interception et extension

Un **Middleware** dans Redux est une fonction intermédiaire qui intercepte toute action envoyée via `dispatch` **avant qu'elle n'atteigne le reducer**.

```
[dispatch(action)] ───> [ Middleware 1 ] ───> [ Middleware 2 ] ───> [ Reducer ] ───> [ Store ]
```

Cas d'usage des middlewares :
* Enregistrer des journaux de logs détaillés des actions (`redux-logger`).
* Intercepter des actions asynchrones pour exécuter des requêtes réseau (`redux-thunk`).
* Contrôler les droits d'accès et bloquer une action si l'utilisateur n'est pas authentifié.

---

### 9.5 Traçabilité avec `redux-logger`
Le middleware `redux-logger` imprime automatiquement dans la console du navigateur chaque action dispatchée, avec l'état exact du store avant l'action (*prev state*), les détails de l'action, et l'état résultant (*next state*).

---

### 9.6 Middleware asynchrone : `redux-thunk` en profondeur

Par défaut, `dispatch()` n'accepte que des objets simples synchrones. **Redux-Thunk** est un middleware qui permet à `dispatch()` d'accepter **une fonction asynchrone**. 

Cette fonction asynchrone reçoit en paramètres `(dispatch, getState)` et peut ainsi orchestrer des appels d'API complexes :

```javascript
// Action Thunk asynchrone complète (Exemple avec Redux classique ou RTK) :
export const chargerProduitsDepuisAPI = () => {
    return async (dispatch, getState) => {
        // 1. On signale le début du chargement
        dispatch({ type: 'produits/chargementEnCours' });

        try {
            const reponse = await fetch("https://fakestoreapi.com/products");
            const donnees = await reponse.json();

            // 2. En cas de succès, on injecte les données
            dispatch({ type: 'produits/succes', payload: donnees });
        } catch (erreur) {
            // 3. En cas d'échec, on transmet l'erreur
            dispatch({ type: 'produits/erreur', payload: erreur.message });
        }
    };
};

// Dans le composant React :
useEffect(() => {
    dispatch(chargerProduitsDepuisAPI()); // Déclenche le Thunk au montage !
}, [dispatch]);
```

### 10.2 Erreurs classiques et comment les résoudre

| Erreur Constatée | Cause Fréquente | Solution Corrective |
| :--- | :--- | :--- |
| **Mon composant ne se met pas à jour après modification du state** | Mutation directe de l'objet/tableau au lieu de créer une nouvelle référence. | Utilisez l'opérateur spread `...` ou la fonction `produce` d'Immer pour créer un nouvel objet. |
| **Boucle infinie d'appels API dans le navigateur** | Le hook `useEffect` n'a pas de tableau de dépendances ou dépend d'un objet réinitialisé à chaque rendu. | Spécifiez un tableau de dépendances strict `[]` ou contenant uniquement les identifiants primitifs. |
| **Warning: Each child in a list should have a unique "key" prop** | Utilisation de `.map()` sans fournir la prop `key` sur l'élément racine retourné. | Ajoutez `key={item.id}` en utilisant un identifiant stable et unique. |
| **Cannot update a component while rendering a different component** | Déclenchement d'un `dispatch()` ou d'une fonction de mise à jour d'état directement dans le corps de rendu d'un composant. | Déplacez l'appel dans un gestionnaire d'événement (`onClick`) ou dans un hook `useEffect`. |

### 10.3 Lexique bilingue du Développeur Front-End Moderne

* **Props (Properties)** : Propriétés en lecture seule transmises d'un parent à un enfant.
* **State** : État local dynamique d'un composant, dont la modification provoque son re-rendu.
* **Lifting State Up (Remontée d'état)** : Déplacer un état dans le composant parent commun le plus proche pour permettre le partage de données entre frères.
* **Prop Drilling** : Mauvaise pratique consistant à faire transiter des props à travers des composants intermédiaires qui n'en ont pas besoin.
* **Single Source of Truth** : Principe garantissant qu'une donnée d'application n'est stockée et gouvernée qu'à un seul endroit (le Store Redux).
* **Pure Function** : Fonction qui, pour les mêmes arguments d'entrée, retourne systématiquement le même résultat sans aucun effet secondaire.
* **Middleware** : Module d'interception placé entre l'action et le reducer pour exécuter des calculs intermédiaires ou de l'asynchronisme.
* **Thunk** : Fonction qui enveloppe une opération asynchrone pour différer son exécution au sein de Redux.
